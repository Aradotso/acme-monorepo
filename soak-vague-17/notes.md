# What makes a good commit message

A good commit message is concise, specific, and useful to someone reviewing history later. Use an imperative subject line that names the change (for example, “Add retry limit to webhook delivery”), then add a body when context is not obvious: explain the motivation, important trade-offs, user-visible effects, or migration and rollout considerations—not a line-by-line description of the diff.

Keep the subject focused and within the project’s conventional length; avoid vague labels such as “fix stuff,” issue-only references, and punctuation or prefixes that conflict with the repository’s conventions. One commit should represent one coherent change, but do not hide multiple related changes behind an over-broad message. Mention breaking changes, compatibility constraints, generated files, security or data implications, and intentionally non-obvious behavior when relevant. If a change is a revert, merge, automated update, or purely mechanical formatting change, say so plainly and identify what it affects. The message should remain accurate even if the implementation evolves during review, and it must never include secrets or sensitive data.
